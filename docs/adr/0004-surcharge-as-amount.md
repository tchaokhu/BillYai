# ส่วนปรับท้ายบิลเก็บเป็นจำนวนเงิน ไม่ใช่เปอร์เซ็นต์

ไวยากรณ์ในแชทไม่มีที่ให้พิมพ์ค่าบริการ และไม่ควรมี (§3): **ยอดที่พิมพ์คือยอดที่จ่ายจริง**
คนที่ถือใบเสร็จอยู่เห็นยอดสุดท้ายชัดที่สุด · พอโหมด `itemized` มีผลรวมรายชิ้นด้วย ค่าบริการ
จึงเป็น **ส่วนต่างระหว่างยอดที่พิมพ์กับผลรวมรายชิ้น** ที่ระบบคำนวณเอง ไม่ใช่ตัวเลขที่ใครกรอก

ส่วนต่างนั้นกลับเป็นเปอร์เซ็นต์ที่ `numeric(5,2)` เก็บได้ไม่ลงตัว:

```
เคสจริง 4 ก.ย. 2026: Σ รายชิ้น = 44000 สตางค์ · ยอดที่พิมพ์ = 48700 สตางค์
pct = 4700 / 44000 = 10.6818...%   →  numeric(5,2) เหลือ 10.68
addSurcharge(44000, 10.68) = 48699 สตางค์   ←  ขาด 1 สตางค์
```

ledger จะเก็บ 486.99 ทั้งที่ใบเสร็จเขียน 487.00 ซึ่งขัด invariant ที่ `CONTEXT.md` บังคับไว้
ว่าผลรวม Share ต้องเท่ากับยอดบิลเป๊ะเสมอ · **เราจึงเก็บ Surcharge เป็นจำนวนเงินสตางค์
(integer) แทนเปอร์เซ็นต์** และให้ `addSurcharge` บวกจำนวนเงินตรงๆ แทนการคูณเปอร์เซ็นต์

## ทางที่ปฏิเสธ

**กระจายส่วนต่างเข้าไปในราคาของแต่ละชิ้น แล้วเก็บ `surcharge_pct = 0`** — ไม่ต้องแตะ schema
เลยและผลรวมลงตัวเป๊ะ แต่ `expense_item.amount_satang` ที่เก็บจะไม่ตรงกับใบเสร็จ (บราวนี่ 30
กลายเป็น 33.20) · การ์ดรายละเอียดคือสิ่งที่ผู้ใช้ขอมาเพื่อ **เทียบกับใบเสร็จในมือ** ตัวเลข
ที่เทียบไม่ได้ทำให้ทั้งการ์ดไร้ประโยชน์

**เก็บเปอร์เซ็นต์สองตำแหน่งแล้วยอมคลาด ≤1 สตางค์** — ถูกที่สุด ไม่ต้องแก้อะไรเลย แต่ผิดที่
ตัวเลขซึ่งเป็นเหตุผลทั้งหมดที่ระบบนี้มีอยู่ · ความคลาดจะโผล่ในการ์ด ในยอดหนี้ และในการทวง
โดยไม่มีใครอธิบายได้ว่ามันมาจากไหน

## ผลที่ตามมา

- **ต้องมี migration ใหม่** เปลี่ยน `expense.surcharge_pct` เป็นจำนวนเงินสตางค์ · **รันทั้ง
  สอง Supabase project ตามลำดับเดียวกัน** (production กับ dev) — เดิมประเมินไว้ว่างานนี้
  ไม่ต้องมี migration เลย ข้อนี้กลับคำนั้น
- `addSurcharge` เป็นสูตรร่วมของทั้งระบบและถูก export ไว้ให้ชั้น persistence ตรวจ invariant
  ซ้ำอีกชั้น — การเปลี่ยนพารามิเตอร์แตะทั้ง `lib/split.ts`, `lib/repo/expenses.ts` และ
  เทสต์ที่ยืนอยู่บนสูตรนั้นทั้งชุด · **ห้ามมีสองสูตรที่ต้องปัดตรงกัน** ซึ่งเป็นเหตุผลเดิมที่
  มันถูก export ออกมาตั้งแต่แรก
- **คอมเมนต์สูตรใน `0001_init.sql` (`Σ amount_satang = round(total_satang * (1 +
  surcharge_pct/100))`) อยู่ใต้เทสต์** — `contract.db.test.ts` (D25) อ่านคอมเมนต์จริง
  แก้สูตรแล้วไม่แก้คอมเมนต์คือเทสต์แดง และต้องแก้ที่คอมเมนต์ ห้ามผ่อนเกณฑ์
- BigInt กับการปัดครึ่งขึ้นใน `addSurcharge` หายไปทั้งก้อน — บวก integer เข้ากับ integer
  ไม่มีอะไรให้ปัด · `pctDecimals` และ `scalePct` ไม่มีที่ใช้อีก
- **การ์ดต้องเขียนบรรทัดค่าบริการเป็นตัวเลขทุกครั้งที่ส่วนต่างไม่ศูนย์** พร้อมเปอร์เซ็นต์
  ที่คำนวณให้ดูเฉยๆ (`ค่าบริการ/VAT 47 (10.7%)`) — เพราะยอดที่พิมพ์ทำหน้าที่ checksum ของ
  รายการรายชิ้น การลืมพิมพ์รายการหนึ่งบรรทัดจะถูกกลืนเข้าไปเป็น "ค่าบริการ" เงียบๆ ถ้าไม่
  เขียนมันออกมาให้เห็น
- **ส่วนต่างติดลบต้องปฏิเสธทันที** — ผลรวมรายชิ้นมากกว่ายอดที่จ่ายจริงแปลว่าจดผิด ไม่ใช่
  ส่วนลด · ร้านที่ไม่มีค่าบริการได้ส่วนต่างศูนย์ ซึ่งถูกต้องและไม่ต้องขึ้นบรรทัดอะไร
- บิลที่ไม่มี Item ไม่มี Surcharge เลย — ไวยากรณ์เดิม (`+ ข้าว 1200`) ยังคืนศูนย์เสมอ
  โดยตั้งใจ ไม่ใช่ของค้าง

## แก้ 2026-09-06 — ตัวเลขนี้พิมพ์เองได้ ติดลบได้ และเปลี่ยนชื่อเป็น Adjustment

สามอย่างเปลี่ยน หลังจากถามว่า "แก้ราคา VAT ได้ไหม" ตอนดูดราฟหน้าจอ M9 ·
**ชื่อไฟล์ยังเป็น `surcharge` เพราะ ADR ที่ถูกอ้างถึงแล้วไม่เปลี่ยนหมายเลขและชื่อไฟล์**

**1. `adjustment_satang` ไม่ใช่ `surcharge_satang`** — คำว่า surcharge แปลว่า "ส่วนที่บวกเพิ่ม"
ซึ่งขัดกับค่าติดลบที่ตอนนี้รับได้ · คอลัมน์ยังไม่มีอยู่จริง (migration `0003` ยังไม่รัน)
การเปลี่ยนชื่อวันนี้จึงฟรี ส่วนพรุ่งนี้ต้องมี migration อีกใบ · การ์ดกับหน้าจอยังเขียนคำที่คน
อ่านออก ("ค่าบริการ/VAT" เมื่อบวก · "ส่วนลด" เมื่อลบ) — ชื่อในโดเมนกับคำบนจอไม่ต้องเป็นคำเดียวกัน
เมื่อคำบนจอเปลี่ยนตามเครื่องหมายของตัวเลข

**2. ช่องนี้พิมพ์เองได้ แต่มันไม่เปลี่ยนยอดที่จ่ายจริง** — ตัวเลขสามตัวผูกกันด้วย
`ยอดที่จ่ายจริง = ผลรวม Item + ส่วนปรับ` แก้ได้แค่สองตัว ตัวที่สามต้องคำนวณ · ถ้าปล่อยให้
ส่วนปรับเป็นตัวตั้งแล้วให้ยอดที่จ่ายจริงเป็นตัวคำนวณ **ตัวทานหายไปทั้งตัว**: ลืมจดรายการ
หนึ่งบรรทัดแล้วบิลลง ledger น้อยกว่าใบเสร็จโดยไม่มีอะไรส่งเสียง · ที่เลือกคือให้ยอดที่จ่ายจริง
เป็นตัวตั้งเสมอ ส่วนค่าที่พิมพ์เองทำหน้าที่ **ตัวทานชั้นที่สอง** — `ยอดที่จ่ายจริง − ส่วนปรับ`
ต้องเท่ากับผลรวม Item ที่นับได้จริง ไม่เท่า = เตือนพร้อมบอกว่าต่างกันเท่าไหร่ · เว้นว่าง =
คำนวณให้เหมือนเดิม · ใบเสร็จร้านพิมพ์ตัวเลขนี้มาให้อยู่แล้ว ตัวทานชั้นที่สองจึงไม่ได้ขอให้ใคร
ทำเลขเพิ่ม

**3. ติดลบได้เมื่อพิมพ์เอง ไม่ได้เมื่อคำนวณ** — ส่วนลด คูปอง ลดสมาชิก เป็นของจริงที่เจอบ่อย
· แต่ค่าติดลบที่**คำนวณ**ออกมาเองยังเป็นความผิดเสมอ เพราะมันแยกไม่ออกจากการจดราคารายชิ้น
เกินหรือจดยอดหัวขาด · เกณฑ์คือ **มีคนตั้งใจพิมพ์หรือไม่** ไม่ใช่เครื่องหมายของตัวเลข

ผลที่ตามมาเพิ่มจากรายการข้างบน:

- **check constraint เปลี่ยน** — ไม่ใช่ `adjustment_satang >= 0` อีกแล้ว · ที่ต้องคุมคือ
  `total_satang + adjustment_satang > 0` (บิลติดลบทั้งใบไม่มีความหมาย) และ `total_satang > 0`
  ตามเดิม
- `distribute` กระจายส่วนปรับติดลบตามสัดส่วนได้อยู่แล้วโดยไม่ต้องแก้ — แต่ **largest-remainder
  กับเศษที่ตกกับ Payer ต้องมีเทสต์ฝั่งลบด้วย** ไม่ใช่ฝั่งบวกอย่างเดียว
- การ์ดและหน้าจอต้องเขียนคำตามเครื่องหมาย และ **ยังต้องแสดงทุกครั้งที่ไม่ศูนย์** ตามเหตุผลเดิม
  (ส่วนปรับที่ไม่ถูกเขียนออกมาคือที่ซ่อนของรายการที่จดตก)

## แก้ 2026-09-06 (สอง) — ตั้งเป็นเปอร์เซ็นต์ก็ได้ แต่เปอร์เซ็นต์ไม่ถูกเก็บ

`บางที่มีเฉพาะ VAT ไม่มี service charge` — จริง และการบังคับให้คนแปลงเป็นบาทเองคือการสั่งให้
ทำเลขโดยไม่จำเป็น ซึ่งเป็นเหตุผลเดียวกับที่ §3 ไม่ให้พิมพ์เปอร์เซ็นต์ตอนจดในแชท

**เปอร์เซ็นต์กลับมาในฐานะเครื่องคิดเลขบนหน้าจอ ไม่ใช่ค่าที่เก็บ** — พิมพ์ `7` แล้วได้
`adjustment_satang = round(ผลรวมรายชิ้น × 7 / 100)` เป็น integer ทันที · สิ่งที่ลงตารางยังเป็น
จำนวนเงินเสมอ ปัญหาการปัดของ `numeric(5,2)` ที่ ADR นี้ตั้งขึ้นมาแก้จึงไม่กลับมา

ส่วนปรับจึงมีสามโหมด **และยอดที่จ่ายจริงเป็นตัวตั้งทุกโหมด**:

| โหมด | ส่วนปรับมาจาก | เกิดอะไรเมื่อรายการเปลี่ยน |
|---|---|---|
| `auto` | `ยอดที่จ่ายจริง − ผลรวมรายชิ้น` | ส่วนปรับขยับ ยอดหัวไม่ขยับ |
| `pct` | `ผลรวมรายชิ้น × %` | **ส่วนปรับคำนวณใหม่ทุกครั้ง** |
| `amount` | เลขที่พิมพ์ | ไม่ขยับเลย |

โหมด `pct` กับ `amount` ทำให้ยอดหัวกลายเป็นตัวทาน: `ยอดที่จ่ายจริง − ส่วนปรับ` ต้องเท่ากับ
ผลรวมรายชิ้นที่นับได้จริง · ลืมจดรายการในโหมด `pct` แล้วผลรวมรายชิ้นเล็กลง ส่วนปรับก็เล็กลงตาม
ผลบวกจึงไม่ถึงยอดหัวและถูกจับได้เหมือนเดิม — **ตัวทานไม่หายไปเพราะเปอร์เซ็นต์**

## ทางที่ปฏิเสธ (รอบเปอร์เซ็นต์)

**เติมยอดที่จ่ายจริงให้อัตโนมัติจาก `ผลรวมรายชิ้น + ส่วนปรับ`** — สะดวกที่สุดและเป็นสิ่งที่
คนจะขอ · แต่มันคือปุ่มที่ทำให้ข้อความเตือนหายไปโดยไม่ต้องแก้อะไร และสิ่งที่หายไปพร้อมกันคือ
รายการที่ลืมจด · ยอดหัวมาจากใบเสร็จเท่านั้น

**แยกช่อง service charge กับ VAT** — ตรงกับที่ใบเสร็จเขียนที่สุด แต่เพิ่มสองช่องพร้อมกฎการทบ
ที่ต้องคุมด้วยเทสต์ (10% แล้ว 7% = 17.7% ไม่ใช่ 17%) และขัดกับ `CONTEXT.md` ที่กำหนดไว้ว่า
Adjustment คือ **หนึ่งจำนวนเงินต่อบิล ไม่แยกว่ามาจากอะไร** · ชิปลัด `7%` `10%` `17.7%` ให้ผล
เดียวกันโดยไม่เพิ่มแนวคิดใหม่ และเลข 17.7 ที่คนไม่รู้ก็ไม่ต้องรู้เพราะมันเป็นปุ่ม
