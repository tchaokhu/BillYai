# Draft ของบิลเก็บในตารางแยก ไม่ยัดใส่ postback data

Draft card ตอบกลับเข้ากลุ่มแล้วรอคนกด "ยืนยัน" จึงลง ledger (D16) — ระหว่างสองจังหวะนั้น
สถานะต้องอยู่ที่ไหนสักที่ **เราเลือกตาราง `expense_draft` แยกต่างหาก** เพราะ postback `data`
ของ LINE จำกัด **300 ตัวอักษร** ซึ่งเป็นเพดานที่ออกแบบให้พ้นไม่ได้ ได้แค่หวังว่าจะไม่ชน และ
มันจะชนตอนบิลใหญ่ที่มีคนหารหลายคน — ซึ่งเป็นกรณีที่ product นี้มีไว้เพื่อพอดี

## ทางที่ปฏิเสธ

**ยัดใส่ postback data** — `+ คอนโด 8000 กอล์ฟx2 เบียร์ ตูน แนน โจ้ #เชียงใหม่` ต้องขน
ยอด ชื่อทุกคน น้ำหนัก split mode surcharge และ event tag · ชื่อไทยกินหลายไบต์ต่อตัวอักษร
ทะลุ 300 เมื่อไหร่ผลคือ **บิลที่คนเยอะที่สุดกดยืนยันไม่ได้** และไม่มีทางรู้ล่วงหน้าว่าจะทะลุ
ตอนไหน

**เขียนลง `expense` เลยแล้วมี `status='draft'`** — ไม่ต้องมีตารางใหม่ก็จริง แต่
`lib/debt.ts`, `lib/repo/ledger.ts`, `expense_share` ทั้งชุดถูกเขียนและเทสต์ไว้แล้วบนสมมติฐาน
ว่าทุกแถวใน `expense` คือของจริง · การเติม `status` ทีหลังคือการเปลี่ยนความหมายของตารางที่มี
เทสต์ 295 ตัวยืนอยู่บนนั้น และการลืมกรอง `status` ที่ query เดียวแปลว่า**ยอดผิดแบบเงียบ**
ซึ่งเป็นความผิดพลาดประเภทที่ ledger รับไม่ได้

## ผลที่ตามมา

- ต้องมี migration ใหม่ และตามกฎของโปรเจกต์ต้องรันใส่ Supabase ทั้งสอง project ตามลำดับเดียวกัน
- draft ที่ไม่มีใครกดยืนยันคือขยะที่ลบทิ้งได้เสมอ ไม่มีใครอ้างถึง — เก็บกวาดด้วย `delete` ธรรมดา
  โดยไม่ต้องกลัวไปโดนของจริง
- postback data เหลือแค่ id ของ draft ซึ่งสั้นและยาวคงที่ ไม่มีวันชนเพดาน 300
- **ตารางนี้เป็นตัวกันบิลลงซ้ำไปในตัว** (ตัดสิน 2026-08-30) — commit คือ `delete draft` +
  `insert expense` ใน transaction เดียว กดยืนยันซ้ำจึงหา draft ไม่เจอแล้วไม่ทำอะไร ทั้งกรณี
  LINE ยิง postback ซ้ำและกรณีคนกดปุ่มรัวเพราะเน็ตช้า · draft id คือตัวแทนของ "เจตนาจะจดบิล
  ใบนี้ครั้งนี้" พอดี และการกดยืนยันคือการบริโภคเจตนานั้น ครั้งเดียวจบ — "กดได้ครั้งเดียว"
  จึงเป็นคุณสมบัติของ DB ไม่ใช่ของโค้ดที่ต้องจำไปเช็ค

  ทางที่ปฏิเสธคือจำ `x-line-retry-key` ไว้ในตาราง ซึ่งกันได้แค่ครึ่งเดียว: มันกัน LINE retry
  (ซึ่งเกิดตอนเราตอบไม่ใช่ 2xx — เราคุมได้เอง) แต่ไม่กันคนกดรัว เพราะนั่นเป็น postback คนละ
  event มี retry key คนละตัว · ส่วน unique constraint บน `expense` ใช้ไม่ได้เพราะไม่มีนิยาม
  ที่ถูกของคำว่า "บิลซ้ำ" — สั่งข้าวสองรอบ ยอดเท่ากัน คนเดียวกัน นาทีเดียวกัน เป็นเรื่องปกติ

  **ช่องที่ยังไม่กันโดยตั้งใจ:** message event ซ้ำจะสร้าง draft สองใบ (การ์ดโผล่สองครั้ง)
  เสียหายแค่ความรำคาญ ไม่แตะ ledger · แก้ด้วย retry key ทีหลังได้ถ้าเจอจริง — ตอนนี้ยังไม่มี
  หลักฐานสักชิ้นว่า LINE retry เกิดกับเรา

- **draft หมดอายุใน 24 ชั่วโมงนับจากตอนสร้าง** (ตัดสิน 2026-08-30) · การ์ดเก่าอยู่ในแชทตลอดไป
  เพราะ LINE ไม่ลบข้อความให้ — เลื่อนแชทขึ้นไปเจอการ์ดของเมื่อสามสัปดาห์ก่อนแล้วกดยืนยัน
  จะได้บิลที่ไม่มีใครตั้งใจจดแล้วลง ledger · กดหลังหมดอายุตอบตรงๆ ว่าการ์ดเก่าแล้วให้พิมพ์ใหม่

  **เหตุผลข้อเดิมของกฎนี้คือวันที่เพี้ยน ซึ่ง D35 ปิดไปแล้วที่ต้นทาง** (`spent_at` ถูกแช่ตั้งแต่
  ตอนสร้าง draft ไม่ใช่ตอน commit) · ที่กฎยังอยู่เพราะเหตุผลที่เหลือยังจริงทั้งหมด: Roster
  เปลี่ยนไปแล้ว ยอดอาจถูกเคลียร์ไปแล้ว และเจตนาของเมื่อสามสัปดาห์ก่อนไม่ใช่เจตนาของตอนกด

  24 ชั่วโมงเพราะสั้นกว่านี้ไม่พอกับสถานการณ์จริง (จ่ายเงิน เดินออกจากร้าน พิมพ์บิล มีคนเรียก
  ไปทำอย่างอื่น กลับมากดตอนถึงบ้าน) และยาวกว่านี้ไม่มีประโยชน์ (ข้ามคืนแล้วยังไม่กด = ลืมจริง
  พิมพ์ใหม่เร็วกว่าเลื่อนแชทหา) · **นับจากเวลาสร้าง ไม่ผูกกับขอบวัน `Asia/Bangkok`** ที่ใช้
  ในที่อื่นของระบบ ไม่งั้นบิลมื้อดึกจะเหลืออายุ 40 นาทีโดยไม่มีเหตุผล

  เก็บกวาดแถวหมดอายุ **ตอนเขียน ไม่ใช่ด้วย cron** — D7 ตั้งใจไว้ว่า v1 ไม่มี cron เลย และขยะ
  ไม่กี่แถวในวงที่เลิกใช้ไม่คุ้มกับการผิดคำนั้น

  **กวาดทุกแถวที่หมดอายุ ไม่เฉพาะของวงตัวเอง** (แก้จากที่ย่อหน้านี้เคยเขียนไว้ ตัดสินตอนลงมือ
  M5) · แถวที่หมดอายุแล้วเป็นขยะไม่ว่าจะของใคร การจำกัดขอบเขตจึงได้แค่ทิ้งงานไว้ให้วงอื่นทำ ·
  และขอบเขต "วงเดียวกัน" ของแชท 1:1 ต้องเขียนเป็นเงื่อนไขบน `line_user_id` แทน `line_group_id`
  ซึ่งทำให้ predicate มีสองรูปแบบโดยไม่ได้อะไรกลับมา · index `expense_draft_created_at_idx`
  มีไว้รับ query นี้โดยเฉพาะ

- **draft ต้องอ้างถึงวงที่ยังไม่เกิดได้** (ตัดสิน 2026-08-30) เพราะวงส่วนตัวเกิดตอนกดยืนยัน
  ไม่ใช่ตอนมีคนทักเข้ามาในแชท 1:1 · ถ้าสร้างวงตั้งแต่ข้อความแรก ทุกคนที่แอดบอทแล้วทักคำเดียว
  แล้วหายไปจะทิ้งแถวเปล่าไว้ถาวร และ `check` ของ `ledger_group` บังคับให้วง `personal` ต้องมี
  `owner_id` หรือ `owner_token_hash` — แปลว่าต้องสร้าง `app_user` ให้ด้วย = สองแถวเปล่าต่อคน
  ที่ทักมาเฉยๆ ในระบบที่ไม่มี hard delete

  ผลคือ draft ในวงกลุ่มชี้กลุ่ม ส่วน draft ใบแรกของวงส่วนตัวชี้ `line_user_id` แทน —
  **ตารางเดียวสองรูปแบบ ซึ่งปกติเป็นสิ่งที่ควรค้าน** ยอมรับตรงนี้เพราะทางเลือกคือขยะถาวรใน
  ตารางที่ลบไม่ได้ · **ข้อกังวลนี้หายไปเองตอนออกแบบตารางจริง (2026-08-30)** — ดูหัวข้อ
  "หน้าตาของตาราง" ท้ายไฟล์ · กฎรวมของระบบคือ **เขียนช้าที่สุดเท่าที่ทำได้ เขียนเมื่อมี
  เจตนาที่ยืนยันแล้วเท่านั้น** — เหมือน D28 ที่ให้ Member เกิดตอน commit ไม่ใช่ตอน draft

  ผลพลอยได้: กฎ "ตอบไกด์เมื่อวงยังไม่มี Expense" ตอบได้โดยไม่ต้อง query เลยในกรณีที่พบบ่อยที่สุด
  — ไม่มีวง = ยังไม่มีบิลแน่นอน

## หน้าตาของตาราง (ตัดสิน 2026-08-30)

```sql
create table expense_draft (
  id             uuid primary key default gen_random_uuid(),
  line_group_id  text,                    -- null = แชท 1:1 (วงส่วนตัว)
  line_user_id   text not null,           -- คนพิมพ์ (D26)
  payload        jsonb not null,          -- ExpenseDraft ที่ต้อง validate ตอนอ่าน
  spent_at       date not null,           -- D35 แช่ตั้งแต่ตอนสร้าง draft
  created_at     timestamptz not null default now()
);
create index on expense_draft (line_group_id, created_at);
create index on expense_draft (created_at);   -- เก็บกวาดของหมดอายุ
```

**payload เป็น `jsonb` ก้อนเดียว ไม่ normalize** — draft ไม่เคยถูก query ตามเนื้อใน ไม่เคย join
ไม่เคย aggregate มันถูกอ่านทั้งก้อนด้วย id เดียวแล้วโยนทิ้ง · การแตกเป็น `expense_draft` +
`expense_draft_participant` คือสองตารางกับสอง write path ต่อหนึ่ง draft โดยไม่ได้ query ที่ทำได้
เพิ่มสักอัน · **ราคาที่ต้องจ่ายคือตอนอ่านกลับต้อง validate เข้ม** แบบเดียวกับที่ narrow JSON ของ
LINE ไม่ใช่ `as ExpenseDraft` — payload ที่เขียนด้วยโค้ดเวอร์ชันก่อนหน้ายังนอนอยู่ในตารางได้ถึง
24 ชั่วโมงหลัง deploy ซึ่งเป็นหน้าต่างที่ยาวพอจะเจอจริง

**ไม่มี `group_id` เลย — ตารางนี้ถือตัวตนฝั่ง LINE อย่างเดียว** (ตัดสิน 2026-08-30 ตอนเริ่ม M5)
· ร่างแรกของ ADR นี้ให้ `group_id` nullable โดยคิดว่าวงกลุ่มมีอยู่แล้วตอน draft มีแต่วงส่วนตัว
ที่ยังไม่เกิด · แต่นั่นแปลว่า "วงเกิดตอนไหน" มีสองคำตอบขึ้นกับชนิดของวง ซึ่งเป็นสิ่งที่ D30
ตั้งใจเลี่ยง ("กฎเดียวใช้ทั้งระบบดีกว่าตัดสินทีละที่") และทำให้กลุ่มที่มีคนพิมพ์บิลแล้วไม่กด
ยืนยันเลยทิ้งแถว `ledger_group` เปล่าไว้ถาวร เพราะวงมีแค่ soft-delete

ผลคือ **`ensureLineGroup` ถูกเรียกตอนกดยืนยัน ไม่ใช่ตอนสร้าง draft** และตารางนี้ไม่มี FK ไป
`ledger_group` ซึ่งรับได้เพราะแถวหมดอายุใน 24 ชั่วโมงอยู่แล้ว · Roster ตอน draft อ่านจาก
`line_group_id` → ไม่มีวง = Roster ว่าง = ทุกคนติดป้าย `(ใหม่)` ซึ่งถูกต้องตาม D28

**`line_user_id` `not null` ทุกใบ ไม่ใช่เฉพาะวงส่วนตัว** — D26 บังคับว่าเฉพาะคนพิมพ์กดยืนยันได้
แปลว่าต้องเก็บว่าใครพิมพ์ไว้ทุกใบอยู่แล้ว รวมทั้งใบที่อยู่ในวงกลุ่ม · พอเก็บอยู่แล้ว "ตารางเดียว
สองรูปแบบ" ที่ย่อหน้าข้างบนยอมรับอย่างไม่เต็มใจก็หายไป เหลือคอลัมน์เดียวที่แปลว่า "ใครพิมพ์"
ซึ่งใช้ตรวจ D26 ได้ทั้งในกลุ่มและใน 1:1 ด้วยโค้ดเส้นเดียว ส่วน `line_group_id is null` แปล
ตรงตัวว่า "มาจากแชท 1:1" ซึ่งเป็นข้อมูลของ LINE ล้วน ไม่ใช่การอ้างถึงวงที่ยังไม่มี
