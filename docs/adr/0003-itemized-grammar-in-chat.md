# ใบเสร็จรายชิ้นจดด้วยไวยากรณ์ในแชท ไม่รอ LIFF

`DESIGN.md` §3 เขียนไว้ว่าโหมด `itemized` เป็นงานของ LIFF ใน Phase 2 — **เรากลับคำนั้น
และให้จดรายชิ้นด้วยไวยากรณ์ในแชทตั้งแต่ Phase 1** โดยรายการแต่ละชิ้นเป็นบรรทัดที่ขึ้นต้น
ด้วย `-` ต่อจากบรรทัดหัวบิลที่ขึ้นต้นด้วย `+`

```
+ soul bingsu 487
- บราวนี่ 30 four nut dear aek
- ฮันนี่โทสต์ 149 game
```

เหตุผลที่ไม่รอ: LIFF ยังไม่มีสักบรรทัดในโค้ด รอมันแปลว่ารอทั้ง Phase 2 ส่วนคณิตศาสตร์
(`lib/split.ts` `itemizedSubtotals`) การตรวจผลรวม และการเขียน/อ่าน `expense_item` +
`expense_item_share` **ทำเสร็จและมีเทสต์คุมอยู่แล้วทั้งหมด** สิ่งที่ขาดคือทางเข้ากับการ์ด
เท่านั้น — งานนี้จึงเป็นการต่อสองปลายที่มีอยู่แล้วเข้าหากัน ไม่ใช่การสร้างโหมดใหม่

## ทางที่ปฏิเสธ

**รอ LIFF ตามแผนเดิม** — ปัญหาถูกเจอตอนยิง M8 จริง (4 ก.ย. 2026) กับใบเสร็จบิงซู 7 รายการ
487 บาท 3 ชุดคนกิน · วิธียุบตามชุดคนกินที่ §3 เขียนไว้ใช้ได้จริงและได้หนี้เท่ากันทุกบาท แต่
สิ่งที่หายไปคือ **รายการรายชิ้น** ซึ่งคือสิ่งเดียวที่ผู้ใช้ขอ · การรอ surface ที่ยังไม่มีอยู่
เพื่อฟีเจอร์ที่ backend ทำเสร็จแล้ว คือการปล่อยของที่พร้อมไว้เฉยๆ

**`+` นำหน้าบรรทัดรายการ** — ชนกับ Trigger จดบิลโดยตรง: ข้อความเดี่ยวที่ขึ้นต้นด้วย `+`
วันนี้คือ "บิลใหม่" แยกจาก "เพิ่มรายการเข้าบิลที่ค้าง" ไม่ได้เลย

**ไม่มีเครื่องหมายนำหน้าบรรทัดรายการ** (ทุกบรรทัดหลังหัวบิลคือรายการโดยปริยาย) — พิมพ์
น้อยกว่าจริง แต่ปุ่มของ LINE ส่งข้อความไม่ได้ การเพิ่มรายการเข้า draft ที่ค้างอยู่จึงต้องมี
คนพิมพ์ และข้อความนั้นมาลอยๆ ไม่มีบรรทัดหัวให้อ้าง — ต้องประดิษฐ์ไวยากรณ์ตัวที่สองสำหรับ
กรณีนั้นอยู่ดี · แถมข้อความหลายบรรทัดที่คนพิมพ์คุยต่อในก้อนเดียวกันจะกลายเป็นรายการเงียบๆ

## ผลที่ตามมา

- **`-` เป็น Trigger ตัวที่สี่** ต่อจาก `+` คีย์เวิร์ด และ @mention · ไม่ต้อง @mention
  ในกลุ่มด้วยเหตุผลเดียวกับที่ D47 ยกเว้น `+`: มันเป็นสัญลักษณ์ ไม่ใช่คำที่คนในกลุ่มพูดกันเอง
  · บรรทัดที่ไม่เข้ารูป `<ชื่อ> <ราคา> [ชื่อคนกิน...]` ตกเป็น `unparsed` แล้วเงียบตามกฎเดิม
- **ราคาในบรรทัด `-` คือเลขตัวสุดท้าย ไม่ใช่ตัวแรกเหมือนหัวบิล** — `- โค้ก 2 ขวด 60 aek`
  ต้องได้ราคา 60 · เอากฎนี้ไปใช้กับหัวบิลไม่ได้ฟรี เพราะ `+ ค่าห้อง 3000 502` วันนี้เงียบ
  (`502` เป็นชื่อคนไม่ได้) แต่ถ้าสแกนจากขวาจะกลายเป็นบิล 502 บาท **ผิดแบบเงียบ** และหัวบิล
  ไม่มีผลรวมรายชิ้นไว้ทาน
- **ใครในวงก็เพิ่มรายการได้ ไม่ใช่แค่คนพิมพ์หัวบิล** — ไม่ชน D26 เพราะ D26 คุมที่ปุ่มยืนยัน
  ไม่ใช่ที่เนื้อ draft · การ์ดถูก render ใหม่กลับเข้ากลุ่มทุกครั้ง เจ้าของ draft เห็นก่อนกดเสมอ
  และ Payer ยังเป็นคนพิมพ์ `+` ไม่ใช่คนเพิ่มรายการ
- **วงหนึ่งมี draft ค้างพร้อมกันได้หลายใบ** (`createDraft` insert เสมอ ไม่มี unique) —
  `-` เดี่ยวๆ จึงต้องถามว่าจะเข้าใบไหนเมื่อมีมากกว่าหนึ่งใบ ถามด้วย quick reply ที่ postback
  พา `draftId` · ระหว่างรอคนกด รายการนั้นเกาะอยู่กับ **draft ทุกใบที่เป็นตัวเลือก** ในรูป
  `pendingItem` แล้วถูกกวาดออกจากใบอื่นตอนเลือกเสร็จ — เกาะใบเดียวแปลว่าใบนั้นถูกยืนยันไป
  ก่อนแล้วรายการหายทั้งที่ตัวเลือกอื่นยังอยู่ · **เฉพาะคนที่พิมพ์ `-` กดปุ่มนี้ได้** คนอื่นกด
  แล้วเงียบ เกณฑ์เดียวกับ D26
- **ตัวรายการเดินทางใน postback ไม่ได้** — ADR 0002 วัดไว้แล้วว่าข้อความไทยผ่าน
  `encodeURIComponent` ยาวขึ้นเก้าเท่าและทะลุ 300 ตัวอักษรตั้งแต่ราว 27 ตัว · นี่คือเหตุผล
  ที่ต้องมี `pendingItem` แทนที่จะขนรายการไปกับปุ่ม
- **`expense_draft.payload` มีสถานะที่สองแล้ว** (`pendingItem`) ซึ่ง ADR 0001 ตั้งใจไม่ให้มี
  · มันถูกกวาดด้วย TTL 24 ชั่วโมงเดียวกับ draft และ `parseStoredDraft` ต้องอ่าน payload
  เวอร์ชันเก่าที่ไม่มีฟิลด์นี้ได้ตลอด 24 ชั่วโมงหลัง deploy
- **ลบรายการเป็นปุ่มต่อแถวบนการ์ด Draft** และ postback พา **id สั้นต่อชิ้น ไม่ใช่ index** —
  การ์ดใบเก่าลอยอยู่ในแชทตลอดกาลและกดได้เสมอ · index จะเลื่อนทุกครั้งที่มีการลบ แล้วการกด
  การ์ดเก่าจะลบผิดชิ้นแบบเงียบ ซึ่งเป็นความผิดชนิดที่ ledger รับไม่ได้
- **รายการที่ไม่ tag ชื่อใครเลยคือของกลาง หารกับทุกคนในบิล** — วันนี้ `itemizedSubtotals`
  โยน error เมื่อ `memberIds` ว่าง (`split.ts:151`) ด่านนั้นยังอยู่ ทางเข้าเป็นคนเติมชื่อ
  ให้ครบก่อนส่งเข้าไป
- **การ์ดที่ยาวเกิน bubble ใช้ carousel ไม่ตัดเป็นบิลใบที่สอง** — ตัดสองบิลทำให้ยอดหัวของ
  แต่ละใบเป็นตัวเลขที่ไม่มีใครพิมพ์ ผลรวมรายชิ้นไม่มีอะไรให้ทาน และถ้ายืนยันสองครั้งแล้วกด
  ใบเดียว **ครึ่งบิลจะลง ledger** · เพดาน carousel (ราว 10 bubble / 50 KB) **ยังไม่ได้ยิงจริง
  ต้องวัดก่อนเชื่อ**
