## S1 — `getGroupMemberProfile` บน OA ที่ยังไม่ verified

**ถามอะไร:** ดึง display name ของคนที่พิมพ์ในกลุ่มได้ไหม โดยที่คนนั้น**ยังไม่ได้เพิ่มบอทเป็นเพื่อน**
และ OA **ยังไม่ verified**

**ทำไมต้องรู้:** D10 (auto-suggest ชื่อตอน claim ตัวตน) วางอยู่บนข้อนี้ทั้งอัน

### ขั้นตอน

1. เชิญบอทเข้ากลุ่ม LINE ที่มีคนอื่นอย่างน้อย 2 คน โดย**อย่างน้อยหนึ่งคนไม่ได้เพิ่มบอทเป็นเพื่อน**
2. รับ webhook event สักอันเพื่อเอา `groupId` กับ `userId` — วิธีเร็วสุดคือชี้ webhook URL ไปที่
   https://webhook.site/ ชั่วคราว แล้วให้คนในกลุ่มพิมพ์อะไรก็ได้ · จด `source.groupId`
   และ `source.userId` ของ**คนที่ไม่ได้เป็นเพื่อนกับบอท**
3. ยิงจากเครื่องตัวเอง:

```bash
curl -i -H "Authorization: Bearer $CHANNEL_ACCESS_TOKEN" \
  "https://api.line.me/v2/bot/group/$GROUP_ID/member/$USER_ID"
```

### บันทึกผล

**ผลจริง 2026-08-26 — ผ่าน**

| ข้อ | ผล |
|---|---|
| HTTP status — `userId` ของคนที่ไม่ได้แอดบอทเป็นเพื่อน | **200** ได้ `displayName` มา |
| HTTP status — `userId` ของตัวเองที่แอดบอทแล้ว | **200** |
| OA verified หรือยัง | **ยังไม่ verified** — บัญชีฟรีที่เพิ่งสร้าง |
| `getGroupMemberIds` (`/members/ids`) | ยังไม่ได้ยิง — เอกสาร LINE ระบุว่าเฉพาะ verified/premium จึงไม่ใช่คำถามเปิด |

**สรุป: D10 ใช้ได้ตามที่ออกแบบไว้** auto-suggest ชื่อตอน claim ตัวตนดึง `displayName`
ได้จริงบนบัญชีฟรี โดยคนนั้นไม่ต้องแอดบอทเป็นเพื่อนก่อน

**แต่ยังต้องรองรับเคสที่ไม่มีชื่อให้ดึง** — เอกสาร LINE ระบุว่าถ้าผู้ใช้ไม่ได้ให้ consent
เข้าถึงโปรไฟล์ webhook จะไม่มี `userId` มาให้เลย auto-suggest จึงเป็นทางลัด ไม่ใช่
ทางเดียว ต้องมีทางให้พิมพ์ชื่อเองเสมอ

เอกสาร LINE ไม่ได้ระบุข้อจำกัด verified/premium ไว้กับ endpoint โปรไฟล์รายคน (ต่างจาก
`/members/ids` ที่ระบุไว้ชัด) — จึงยังเป็นคำถามเปิดที่ต้องยิงจริง

อีกข้อที่เอกสารระบุไว้และกระทบ D10 ตรงๆ: ถ้าผู้ใช้ไม่ได้ให้ consent เข้าถึงโปรไฟล์
webhook จะ **ไม่มี `userId`** มาให้เลย — ระบบต้องรับสภาพนั้นได้ ไม่ใช่แค่เคส API ตอบ error

เกณฑ์ตอนตั้งไว้: 200 พร้อม `displayName` → D10 เดินตามแผนเดิม · 403/404 → ต้องแก้ D10
ผลออกมาเป็นทางแรก **ไม่ต้องแก้ `docs/DESIGN.md`**

## S2 — `liff.sendMessages()` จาก group context

**ถามอะไร:** เปิด LIFF จากในแชทกลุ่มแล้วสั่งส่งข้อความเข้ากลุ่มนั้นได้จริงไหม
ขออนุญาต scope เด้งกี่ครั้ง หน้าตาแบบไหน

**ทำไมต้องรู้:** D7 (Nudge ผ่าน LIFF) วางบนข้อนี้ · ถ้า friction สูงเกิน ถอยไปใช้ Nudge Link (D20)
เป็นช่องทางหลัก — ไม่ถึงกับพังทั้งข้อ

### ขั้นตอน

1. deploy หน้าที่เรียก `liff.init()` แล้วมีปุ่มเรียก `liff.sendMessages()`
   — **ทำแล้ว** `app/liff/spike/page.tsx` (M3) · ต้องสร้าง LIFF app แล้วติ๊ก scope
   `chat_message.write` ก่อน ขั้นตอนอยู่ที่ `docs/SETUP-DEPLOY.md` §4
2. เอา LIFF URL (`https://liff.line.me/<liffId>`) ไปวางในแชท**กลุ่ม** แล้วกดจากในกลุ่ม
3. กดปุ่มส่ง แล้วสังเกต

### บันทึกผล

| ข้อ | ผล |
|---|---|
| `liff.getContext().type` ที่ได้ตอนเปิดจากกลุ่ม | _ยังไม่ได้ทำ_ |
| ขึ้นหน้าขออนุญาตกี่ครั้ง / ครั้งแรกเท่านั้นหรือทุกครั้ง | _ยังไม่ได้ทำ_ |
| ข้อความไปโผล่ในกลุ่มจริงไหม ชื่อผู้ส่งขึ้นเป็นใคร | _ยังไม่ได้ทำ_ |
| นับเป็น push message ของ OA ไหม (ดู quota ก่อน/หลัง) | _ยังไม่ได้ทำ_ |
| เปิด LIFF URL เดียวกันจากแชท 1:1 ได้ผลต่างกันไหม | _ยังไม่ได้ทำ_ |

ข้อ "นับ quota ไหม" สำคัญกับ C2 — ถ้านับ zero-push ก็ไม่ zero จริง

## S3 — PromptPay EMVCo payload + amount

**ถามอะไร:** payload ที่เราสร้างเอง สแกนด้วยแอปธนาคารจริงแล้วขึ้นชื่อผู้รับถูก **และยอดขึ้นถูก** ไหม

**ทำไมต้องรู้:** ถ้ายอดไม่ขึ้น ผู้จ่ายต้องกรอกเอง = พิมพ์ผิดได้ = value หลักของ Nudge หายไปครึ่ง

โค้ดอยู่ที่ `lib/promptpay/emv.ts` (เทสต์ 22 ข้อใน `emv.test.ts` · CRC มีอิมพลีเมนต์อิสระในเทสต์ไว้เทียบ)
**เทสต์ยืนยันได้แค่ว่าเราสร้างสตริงตามสเปก ไม่ได้ยืนยันว่าแอปธนาคารอ่านออก** — ข้อนั้นต้องสแกนจริง

### ขั้นตอน

```bash
npm run spike:s3 -- <เบอร์พร้อมเพย์ของคุณ> 0.01 12.34 100 1250.50
```

ไฟล์ PNG ออกที่ `spike-out/` (gitignore ไว้แล้ว เพราะ QR มีเบอร์จริงฝังอยู่)
แต่ละยอดออกสองใบ **ลำดับ tag ต่างกัน**:

- `-ascending` — เรียง tag จากน้อยไปมาก (`53` สกุลเงิน → `54` ยอด → `58` ประเทศ) ตามตัวอย่างในสเปก
- `-countryFirst` — เอา `58` ขึ้นก่อน แบบที่ generator พร้อมเพย์ยอดนิยมหลายเจ้าใช้

สเปก EMVCo ไม่ได้บังคับลำดับ แต่แอปธนาคารเป็นคนตัดสิน **นี่คือคำถามหลักของ S3**

เปิดรูปบนจอคอม แล้วสแกนด้วยแอปธนาคาร **อย่างน้อย 3 เจ้า** (คนละแอปจริงๆ ไม่ใช่ 3 บัญชีในแอปเดียว)

payload ที่สคริปต์พิมพ์ออกจอ **ปิดเบอร์ไว้เหลือสี่ตัวท้าย** จึงแปะลงไฟล์นี้ได้เลย ·
ถ้าต้องเทียบกับ generator เจ้าอื่นให้เติม `--show-payload` แต่ผลที่ได้ **ห้ามแปะลงไฟล์ที่ commit**
เพราะมีเบอร์ครบทุกหลัก (D12)

### บันทึกผล

**ผลจริง 2026-08-26 — ผ่าน**

| ธนาคาร | ลำดับ tag | สแกนติด | ยอดขึ้นเอง |
|---|---|---|---|
| กสิกรไทย | ทั้ง `ascending` และ `countryFirst` | ได้ | **ขึ้นเลขให้เอง** |
| เกียรตินาคินภัทร | ทั้งสองแบบ | ได้ | **ขึ้นเลขให้เอง** |
| ttb | ทั้งสองแบบ | ได้ | **ขึ้นเลขให้เอง** |

**สรุปสองข้อที่ S3 ตั้งไว้:**

1. **ยอดขึ้นเอง** ทั้งสามเจ้า → Nudge เก็บ value เต็ม ผู้จ่ายไม่ต้องพิมพ์ยอดเอง
   **ไม่ต้องทบทวน D2**
2. **ลำดับ tag ไม่มีผล** ทั้งสามเจ้าอ่านได้ทั้งสองแบบ → คง default เป็น `ascending`
   (ตรงตัวอย่างในสเปก EMVCo) และ**เก็บตัวเลือก `order` ไว้** เพราะกลุ่มตัวอย่างมีแค่
   สามเจ้า ธนาคารที่ยังไม่ได้ลองอาจเลือกข้าง — ตัวเลือกนี้คือทางถอยที่ไม่ต้องแก้โค้ด

เคสที่ต้องมีในตารางให้ครบ:

- ยอด **ไม่ระบุ** — ต้องเปิดช่องให้กรอกเอง ไม่ใช่ error
- ยอด **0.01** — ขอบล่าง สตางค์ไม่หาย
- ยอดที่มี **สตางค์ไม่ลงตัว** เช่น `12.34` — ตัวเลขไม่โดนปัด
- ยอด **หลักพัน** — ไม่มีคอมมาแทรกจนอ่านผิด

**ถ้าแอปไหนอ่านได้ลำดับเดียว** → ล็อก default เป็นลำดับนั้นใน `emv.ts` แล้วเขียนเหตุผลไว้ในโค้ด
**ถ้ายอดไม่ขึ้นเลยทุกเจ้า** → กลับไปทบทวน D2 ว่า Nudge จะยังมี value พอไหม

## S4 — Vercel cold start + Supabase free

**ถามอะไร:** ตอบ webhook ทันเวลาที่ LINE รอไหม ตอนที่ function เย็นและ DB เย็นพร้อมกัน

**ทำไมต้องรู้:** ถ้าไม่ทัน LINE จะ retry ทำให้บิลถูกจดซ้ำ (หรือต้องทำ idempotency ที่ยังไม่ได้ออกแบบ)

### ขั้นตอน

1. deploy route ที่ทำงานเหมือนของจริงให้ครบเส้น: verify signature → query Supabase หนึ่งครั้ง → ตอบ 200
   — **ทำแล้ว** `app/api/line/webhook/route.ts` (M3) ขั้นตอน deploy อยู่ที่ `docs/SETUP-DEPLOY.md`
2. **ปล่อยทิ้งไว้อย่างน้อย 30 นาที** ให้ทั้ง function และ Supabase free เย็นจริง (free tier พัก DB เอง)
3. วัดจากเครื่องนอก — **คำสั่งเต็มอยู่ใน `docs/SETUP-DEPLOY.md` §5**

**ต้องเซ็นลายเซ็นให้ถูกต้อง** ห้ามส่ง `x-line-signature: dummy` แบบที่ร่างแรกของเอกสารนี้
เขียนไว้ เพราะ route ปฏิเสธตั้งแต่ก่อนแตะ DB (ซึ่งเป็นพฤติกรรมที่ถูก — ไม่งั้นใครก็ปลุก
Supabase free ให้หมดโควตาได้) ตัวเลขที่ได้จะเป็น cold start ของ function ล้วน **ไม่รวม
เวลาปลุก DB** ซึ่งเป็นครึ่งหนึ่งของคำถาม

route ตอบ header `Server-Timing: db;dur=… total;dur=…` — เวลาฝั่ง server ล้วน เอาไปลบ
ออกจาก `time_total` ของ curl แล้วได้ค่าเน็ต + cold start ของ function แยกกัน

ครั้งแรกคือ cold ที่เหลือคือ warm · ทำซ้ำอีกรอบหลังทิ้งไว้ 30 นาทีเพื่อยืนยันว่าไม่ใช่ฟลุ๊ก

### บันทึกผล

**ผลจริง 2026-08-27 — ผ่าน** · `npm run spike:s4 -- https://bill-yai.vercel.app/api/line/webhook`
ยิงจากเน็ตบ้านในไทย ไป Vercel `sin1` + Supabase `ap-southeast-1`

| # | status | wall | server | db | wall − server |
|---|---|---|---|---|---|
| 1 (cold) | 200 | **1296.9** | 117.7 | 117.2 | 1179.2 |
| 2 | 200 | 172.9 | 4.4 | 4.3 | 168.5 |
| 3 | 200 | 400.4 | 3.8 | 3.7 | 396.6 |
| 4 | 200 | 153.2 | 3.6 | 3.5 | 149.6 |
| 5 | 200 | 146.8 | 3.7 | 3.6 | 143.1 |

หน่วยเป็น ms · `server` มาจาก header `Server-Timing` ที่ route ตอบกลับ · `db` คือส่วนที่รอ Supabase

| ข้อ | ผล |
|---|---|
| cold start ครั้งแรก | **1.30 วินาที** (ในนั้นเป็นงานฝั่ง server แค่ 0.12 วิ ที่เหลือคือปลุก function + เน็ต) |
| warm ครั้งที่ 2–5 | **0.15 วินาที** (มัธยฐาน) · งานฝั่ง server 3.6–4.4 ms |
| cold หลัง Supabase พักตัว | ไม่ได้วัดแยก — free tier พักโปรเจกต์เมื่อไม่มีทราฟฟิก **ระดับสัปดาห์** ไม่ใช่ระดับ 30 นาที ค่า `db` 117 ms ในครั้งที่ 1 คือค่าเปิด connection + TLS ไปที่ Supavisor ไม่ใช่ค่าปลุก DB ที่หลับ |
| LINE retry จริงไหม | **ยังไม่มีหลักฐาน** — เอกสาร LINE ระบุเองว่า "จำนวนและช่วงเวลาของการส่งซ้ำไม่เปิดเผย และเปลี่ยนได้โดยไม่แจ้ง" จึงไม่มีเกณฑ์ตัวเลขให้เทียบ |
| region | Vercel `sin1` (ยืนยันจาก header `X-Vercel-Id: sin1::…`) · Supabase `ap-southeast-1` |

**สรุป: D14 อยู่ได้ ไม่ต้องย้าย host ไม่ต้องทำ warm ping**

ตัวเลขที่ตัดสินคือ `server` ไม่ใช่ `wall` — `wall` รวมเวลาเดินทางจากเน็ตบ้านในไทยไปสิงคโปร์
ซึ่ง**LINE ไม่ได้จ่ายค่านี้** เพราะยิงมาจากศูนย์ข้อมูลของตัวเอง งานที่เราคุมได้จริงคือ
3.6–4.4 ms ตอน warm และ 118 ms ตอน cold ส่วนที่ LINE ต้องรอเพิ่มคือเวลาปลุก function
ซึ่งประมาณได้จากส่วนต่าง cold กับ warm ของช่อง `wall − server` ≈ **1.0 วินาที**

ครั้งที่ 3 กระโดดไป 400 ms ทั้งที่ `server` แค่ 3.8 ms — ความแกว่งอยู่ที่เน็ตฝั่งเรา ไม่ใช่ฝั่ง server

**ความเสี่ยงย้ายที่ ไม่ได้หายไป** — เอกสาร LINE แนะนำตรงๆ ว่าให้ประมวลผล webhook
แบบ asynchronous เพื่อไม่ให้ request ถัดไปต้องรอ ตอนนี้เส้นทางมีแค่ verify + query เดียว
จึงเร็ว แต่ Phase 1 จะแทรก **Haiku fallback (D17)** เข้ามาในเส้นเดียวกัน ซึ่งกินเวลาระดับวินาที
ไม่ใช่มิลลิวินาที ถ้าปล่อยให้ LLM อยู่ก่อนการตอบ 200 เราจะย้ายตัวเองกลับเข้าไปในเขตอันตราย
ที่ spike นี้เพิ่งพิสูจน์ว่าตอนนี้ยังไม่อยู่

**สิ่งที่ต้องตัดสินตอนเข้า Phase 1 ไม่ใช่ตอนนี้:** ตอบ 200 ทันทีแล้วทำงานต่อ background
