Member เกิด, คนพิมพ์ claim ตัวตนของตัวเองในจังหวะเดียวกับที่กดยืนยัน

**นี่คือก้อนเดียวในโปรเจกต์ที่แตะเงินจริง** ทุกอย่างก่อนหน้านี้อ่านอย่างเดียว · รอยต่อนี้
คือรอยต่อของ D28 ("อ่านตอน draft เขียนตอนยืนยัน") ซึ่งเป็นเหตุผลที่ M5 กับ M6 แยกกัน

## สิ่งที่ทำ

### 1. รู้ให้ได้ว่าคนพิมพ์คือ Member ตัวไหน (D29 / ADR 0002)

**ต้องรู้ตั้งแต่ตอน draft ไม่ใช่ตอน commit** — เพราะยอดบนการ์ดขึ้นกับว่าคนจ่ายร่วมหารไหม

- repo ใหม่: หา Member จาก `line_user_id` ในวงหนึ่ง (join `app_user` → `member`)
  · ไม่มีวง หรือยังไม่ claim = `null`
- `null` แปลว่า **การ์ดใบนี้คือใบแรกของเขาในวงนี้** → ต้องมีแถวเลือกตัวตน

### 2. แถวเลือกตัวตนเป็น **quick reply** ไม่ใช่ปุ่มบนการ์ด

เอกสาร LINE: quick reply ใส่ได้ **13 ปุ่มต่อข้อความ** ติดกับ message ชนิดไหนก็ได้
และรับ postback action

- การ์ดยังมีปุ่ม `ยืนยัน` ปุ่มเดียวเหมือนเดิม — ความสูงไม่โตตามจำนวนคนในวง
- quick reply = ชื่อ Member ที่**ยังไม่มีเจ้าของ** ในวง (สูงสุด 12) + `ฉันเป็นคนใหม่`
- คนที่ claim แล้วไม่ต้องเห็นแถวนี้เลย — กด `ยืนยัน` ตรงๆ ได้

### 3. `ฉันเป็นคนใหม่` ใช้ **LINE display name**

S1 ยิงจริงแล้ว: `GET /v2/bot/group/{groupId}/member/{userId}` ตอบ **200 พร้อม
`displayName`** บน OA ที่ยังไม่ verified และคนนั้นไม่ต้องแอดบอทเป็นเพื่อน
(`docs/SPIKE-PHASE0.md` §S1) · ใน 1:1 ใช้ `GET /v2/bot/profile/{userId}`

เลือกทางนี้เพราะ**ไม่มีรอบการโต้ตอบเพิ่ม** ซึ่งเป็นเหตุผลทั้งหมดที่ ADR 0002 เลือกถาม
บนการ์ดที่เขากำลังจะกดอยู่แล้ว · ชื่อ LINE อาจเป็น `Golf⚽️| ไปไหนดี` ซึ่งไม่สวย แต่
**เขาเลือกเอง ไม่ใช่เราเดา** ซึ่งเป็นเส้นที่ ADR 0002 ขีดไว้

- ดึงชื่อไม่ได้ (ไม่มี consent) → ตอบว่ายังจดให้ไม่ได้ · **ห้ามเดาชื่อแทน**
- ชื่อชนกับ Member ที่มีอยู่แล้วในวง → `unique (group_id, display_name)` ปฏิเสธ
  · ตอบให้ชัดว่าชื่อนี้มีคนใช้แล้ว ให้กดเลือกชื่อนั้นแทน

### 4. **คนจ่ายเป็นส่วนหนึ่งของ "ทุกคน" เสมอ** — ปิด finding ที่ค้างจาก M5

`+ ข้าว 1200` ในวงที่มี `กอล์ฟ` `ตูน` แล้วคนพิมพ์ยังไม่ claim: M5 หาร 2 ทาง คนจ่าย
ไม่โดนอะไรเลย และ `+ ข้าว 1200 รวมฉัน` ให้ผลเดียวกันเป๊ะ = `รวมฉัน` ไม่มีผล

**แก้เป็น: ไม่ระบุชื่อใคร = หารกันระหว่าง Roster กับคนจ่าย** · คนที่ claim แล้วอยู่ใน
Roster อยู่แล้วจึงไม่เพิ่มแถวซ้ำ ส่วนคนที่ยังไม่ claim ได้แถวของตัวเอง — ซึ่งตรงกับ
ความจริงว่าเขาก็กินด้วย · `รวมฉัน` ที่ไม่มีชื่อใครจึงกลายเป็นคำที่ซ้ำซ้อนแต่ไม่ผิด
**ไม่ต้องแตะ parser และไม่ต้องเพิ่มฟิลด์ใน `ParseResult`**

ระบุชื่อคนแล้วยังเหมือนเดิม: คนจ่ายไม่ร่วมหารเว้นแต่พิมพ์ `รวมฉัน` (§3 ของ DESIGN)

### 5. เส้นทางกดยืนยัน

postback `data` = `confirm=<draftId>` หรือ `confirm=<draftId>&as=<memberId|new>`
— สั้นและยาวคงที่ ไม่ชนเพดาน 300 ตัวอักษร

ลำดับที่ต้องเป็นแบบนี้เป๊ะ:

1. อ่าน draft · ไม่เจอ/หมดอายุ/payload พัง → ตอบว่าการ์ดเก่าแล้ว ให้พิมพ์ใหม่
2. **`draft.line_user_id` ต้องตรงกับคนกด** (D26) · ไม่ตรง → **เงียบ** ไม่ตอบว่า
   "ไม่มีสิทธิ์" เพราะการประกาศแบบนั้นในกลุ่มเพื่อนคือการทำให้เสียหน้าโดยไม่จำเป็น
3. เปิด transaction เดียว ทำให้ครบ:
   - วงเกิดตรงนี้ — `ensureLineGroup` หรือสร้างวงส่วนตัว + `app_user` (D30)
   - Member ของคนจ่ายเกิดหรือถูก claim
   - `ensureMembers` สำหรับชื่อที่หารด้วย
   - `splitExpense` → `commitExpense`
   - **`deleteDraft` ใน transaction เดียวกัน** — นี่คือกลไกกันบิลลงซ้ำทั้งหมด
     (ADR 0001) กดซ้ำจะหา draft ไม่เจอแล้วไม่ทำอะไร
4. ตอบสรุปกลับเข้ากลุ่ม · **ยังไม่มี Passive Nag** (Phase 2)

### 6. ของที่ต้องกันให้ได้

- **กดสองครั้งรัวๆ** → `deleteDraft` ใน transaction เป็นตัวกัน ต้องมีเทสต์ยิงพร้อมกัน
- **DB พังกลางทาง** → transaction rollback ทั้งก้อน draft ยังอยู่ กดใหม่ได้ ·
  ตอบ 500 ตามเกณฑ์ "เขียนลงไปแล้วหรือยัง" (D36) — ตรงนี้ยังไม่ได้ commit
- **การ์ดเก่ากว่า 24 ชม.** → `findDraft` คืน `null` อยู่แล้ว
- **ยอดต้องตรงกับที่การ์ดโชว์** — draft เก็บ payload ตอนสร้าง Roster อาจโตขึ้นระหว่างนั้น
  · **ใช้ payload ที่แช่ไว้ ไม่ใช่ Roster ณ ตอนกด** ไม่งั้นคนกดยืนยันตัวเลขหนึ่งแล้วได้อีกตัวเลข

### 7. เอา `expense` ออกจากรายการ "ยังไม่เปิดใช้"

`lib/flow/dispatch.ts` เป็นที่เดียว — ไม่มีอะไรต้องไล่แก้ที่อื่น

## ที่ต่างจากแผนตอนลงมือจริง

- **`lines` ถูกเก็บลง payload ของ draft** — แผนบอกให้ "ใช้ payload ที่แช่ไว้" แต่ตอนนั้น
  payload มีแค่ `ExpenseDraft` ซึ่งยังต้องคำนวณต่อด้วย Roster · เก็บผลหารที่คำนวณเสร็จแล้ว
  ลงไปด้วยทำให้ตอนยืนยันไม่ต้องคำนวณอะไรอีกเลย แค่ map ชื่อเป็น Member
- **postback พา member id ไม่ใช่ชื่อ** — ดู ADR 0002 ท้ายไฟล์
- **การ์ดของคนที่ยังไม่ยืนยันตัวตนไม่มีปุ่ม `ยืนยัน`** — ดู ADR 0002 ท้ายไฟล์
- `confirmDraft` รับ `payer` เป็น optional แล้วคืน `needs-identity` เมื่อไม่รู้ว่าใครจ่าย
  แทนที่จะให้ webhook เดาแทน — ด่านนี้อยู่ก่อนการเขียนทุกบรรทัด รวมถึงก่อนลบ draft
- **ด่านที่ล้มเหลวทุกอันต้องอยู่ก่อน `deleteDraft`** — เขียนครั้งแรกไว้หลัง แล้วพบว่า
  `return` ธรรมดาจะทำให้ transaction commit การลบนั้นไปด้วย = การ์ดหายทั้งที่บิลไม่ได้ลง

## ของค้างที่รอบหน้าต้องรับไป

**วงที่มีคนยังไม่ claim เกิน 12 คน** — quick reply ใส่ได้ 13 ปุ่ม เหลือ 12 ช่องให้ชื่อ ·
ตอนนี้เรียง**ใหม่ก่อน** เพราะคนที่กำลังจะเลือกชื่อตัวเองมักเพิ่งถูกพิมพ์ชื่อเข้ามาไม่กี่บิลก่อน
แต่ยังไม่ได้แก้ทั้งหมด: วง 15 คนที่ชื่อของเขาอยู่อันดับ 13 จะเหลือทางเดียวคือ `ฉันเป็นคนใหม่`
ซึ่งสร้าง Member ที่สองให้เขา แล้วหนี้ที่ค้างอยู่บน Placeholder เดิมจะกลายเป็นของคนละคน
ถาวร (D18 ห้ามลบ) · ทางแก้ที่ยังไม่ได้ทำ: แบ่งหน้า หรือให้พิมพ์ชื่อค้นหา

**payload รูปแบบเก่าใช้ไม่ได้แล้ว** — draft ที่เขียนก่อน M6 เก็บ `ExpenseDraft` เปล่าๆ ส่วน
`parseStoredDraft` ต้องการ `{ draft, lines }` · การ์ดที่ค้างอยู่ในแชทตอน deploy จะตอบว่า
"ใช้ไม่ได้แล้ว" ทั้งหมด **ยอมรับได้เพราะยังไม่เคย deploy migration `0002` ขึ้น Supabase เลย**
— ถ้าเคยแล้วต้องเขียน fallback ก่อน
